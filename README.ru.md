# Maintain Server Containers

[English version](README.md)

**Универсальный Agent Skill для регламентного обслуживания Docker Compose с обязательным сохранением пользовательских данных.**

Репозиторий: `agent-maintain-server-containers`

Имя навыка: `maintain-server-containers`

Вызов: `$maintain-server-containers`

**Статус: v0.2.0 (12.10.2026).** Публикация репозитория сама по себе не обновляет ранее установленную копию Agent Skill: установка или обновление выполняются отдельно. В комплекте есть исполняемый анализатор политики, а также режимы read-only аудита, статуса и планирования. Навык содержит регламент обновления, исполняемый агентом с разрешёнными инструментами, но **пока не содержит отдельного программного исполнителя, автоматически изменяющего production Docker**. Успешная проверка YAML не доказывает готовность к обновлению.

## Аудит архитектуры и безопасности (13 октября 2026)

Текущее состояние исходного кода и синтетического CI до H31 рассмотрено в
[отчёте об аудите](docs/SECURITY-ARCHITECTURE-AUDIT-2026-10-13.md).
Подтверждены работа read-only версии v0.2.0 и испытания экспериментальных
контрактов восстановления, но **не подтверждена готовность** к изменению
production-контейнеров: отсутствуют программный исполнитель изменений,
независимое off-host хранилище и реально защищённый источник актуальной
контрольной записи. Обновление репозитория не обновляет установленную
отдельно копию навыка. Следующий этап — ограниченные исправления и
финализация документации, а не создание новых уровней доказательств.

## Исправления по аудиту (PR #22)

По итогам [аудита архитектуры от 13 октября](docs/SECURITY-ARCHITECTURE-AUDIT-2026-10-13.md)
валидация переносимой политики v1 стала строже: неизвестные поля,
включая дополнительные правила безопасности, теперь приводят к ошибке,
а не молча игнорируются. Для расширений проекта требуется явно
проверенная нормализация или именованная политика проекта. Некорректные
синтетические runtime-данные отклоняются; режим `--live` считывает
только необходимую часть Docker Inspect.

**Ограничения поставки:** обновление исходников в GitHub не обновляет
установленную копию навыка. Версии зависимостей и инструментов CI
пока не зафиксированы в полностью воспроизводимом пакете; контроль
целостности установки остаётся отдельной задачей. Даже успешный CI
не означает готовность к автоматическому изменению production Docker:
исполнитель изменений, независимое off-host хранилище и защищённый
внешний источник контрольных записей пока отсутствуют.

## Зачем нужен навык

Обновление Docker-сервиса не должно сводиться к скачиванию `latest`. В контейнерах живут приложения с базами данных, учётными записями, пользовательскими файлами, ключами шифрования, томами и зависимостями. Некоторые новые версии выполняют необратимые миграции.

Цель навыка: сделать обслуживание **полуавтоматическим, понятным и воспроизводимым**. Один запрос пользователя должен разрешать заранее ограниченную последовательность штатных действий без бесконечных уточнений. При этом защита данных, границы доступа и возможность восстановления остаются обязательными.

## Возможности

- Обнаружение Docker Compose-сервисов, конфигураций и ответственных проектов.
- Создание проектной политики обслуживания.
- Проверка image, текущего runtime, health, томов и расхождений между политикой и развертыванием.
- Подготовка плана обновлений с учётом официальных upstream-релизов.
- Разделение сервисов на `AUTO_SAFE`, `AUTO_GATED`, `MANUAL`, `PIN_ONLY` и `NO_TOUCH`.
- Определение резервного копирования, проверки восстановления и правил rollback.
- Регламент поэтапных обновлений с проверкой пользовательского состояния.
- Отдельный отчёт об изменении приложений, контейнеров, данных, сети и схем БД.

Навык не содержит частных IP-адресов, конфигураций конкретного сервера или секретов.

**Совместимость с расширенными политиками:** помимо переносимой схемы `schema_version: "1"`, валидатор поддерживает именованные проектные схемы `<project>-maintenance/v1`, содержащие `policy_class`, `identity.compose_services`, `state_contract.completeness` и группы зависимостей. Исходный файл не переписывается. См. [синтетический пример](examples/native-policy.yaml). Совместимость формата не означает разрешение на обновление.

## Установка

Совместимые с Agent Skills агенты используют канонический каталог:

```text
skills/maintain-server-containers/
  SKILL.md
  agents/openai.yaml
  references/
  scripts/
```

Для Codex каталог помещается в предусмотренное расположение пользовательских или проектных навыков. Для Claude Code предусмотрены plugin-манифест и совместимая структура. Конкретные шаги установки зависят от актуальной версии агента.

Для локального валидатора нужны Python 3.10+ и PyYAML:

```sh
python -m pip install -r skills/maintain-server-containers/scripts/requirements.txt
python skills/maintain-server-containers/scripts/maintenance.py --policy examples/services.yaml validate
python skills/maintain-server-containers/scripts/maintenance.py --policy examples/services.yaml plan
python skills/maintain-server-containers/scripts/maintenance.py --policy examples/native-policy.yaml validate
```

Чтение реальных Docker-метаданных без изменения состояния:

```sh
python skills/maintain-server-containers/scripts/maintenance.py --policy maintenance/services.yaml --live audit
python skills/maintain-server-containers/scripts/maintenance.py --policy maintenance/services.yaml --live --format json status
```

Параметры `--live` и `--format` следует ставить перед именем операции. Используются только Docker `ps` и `inspect` в режиме чтения.

## Примеры использования в чате

**Проверить сервер, ничего не меняя:**

```text
$maintain-server-containers audit
Проверь состояние контейнеров, версии, тома и риски. Никаких изменений.
```

**Подготовить обновления:**

```text
$maintain-server-containers plan
Найди актуальные официальные версии и предложи допустимые обновления по группам.
```

**Одна команда на разрешённую цепочку:**

```text
$maintain-server-containers update-auto
Обнови все допустимые политикой сервисы, сохрани данные и выполни проверки.
Заблокированные, MANUAL и NO_TOUCH пропусти.
```

Последний пример описывает обращение **к агенту**, а не к bundled Python CLI. Агент должен иметь доступ к нужным инструментам развертывания и резервного копирования и не имеет права обходить обязательные проверки.


## Установка нового стороннего приложения из репозитория

Режим `deploy-repository` нужен, когда требуется впервые развернуть
стороннее приложение из GitHub или другого Git-источника:

```text
$maintain-server-containers deploy-repository https://github.com/example-org/example-app
Установи приложение на сервере через Docker Compose, настрой зависимости
и постоянное хранилище, проверь запуск и зарегистрируй в политике обслуживания.
```

Агент изучает репозиторий и требования приложения, выбирает фиксированную
воспроизводимую версию, проверяет конфликты портов и томов, подготавливает
Compose и защищённую конфигурацию, устанавливает приложение и выполняет
health/smoke-проверки. Затем он фиксирует deployment в **существующей**
системе учёта сервера.

**Одного поручения достаточно** для обычных безопасных шагов. Но агент
не вправе самовольно включать `privileged`, давать доступ к Docker socket,
монтировать чужие данные с правом записи, открывать админку в интернет
или переписывать работающие сервисы. Неизвестные внешние учётные данные
и существенные изменения прав требуют одного конкретного уточнения,
а не серии бессодержательных запросов.

Новый сервис первоначально попадает в `MANUAL`, пока не доказаны
условия более автоматического обслуживания. Отсутствие других
Agent Skills не должно препятствовать установке или портить проектную память.

Подробнее: [регламент первого развёртывания](skills/maintain-server-containers/references/repository-deployment.md).
Пока это **агентный workflow**, а не реализованный в Python установщик Docker.


## Развёртывание собственных проектов

Для проектов, новые версии которых создаются в отдельном рабочем репозитории,
предусмотрен режим агента:

```text
$maintain-server-containers deploy-project local-editor
Разверни последнюю подтверждённую сборку, проверь приложение
и синхронизируй записи deployment и проектную память.
```

Поддерживаются приватные Git-репозитории, локальные сборки и артефакты CI
вне сервера. Агент ищет **утверждённый пригодный к развёртыванию релиз**,
а не просто последний commit, проверяет воспроизводимую Compose-конфигурацию,
сохранность данных, backup/restore, миграции и фактический результат.

После подтверждённого развёртывания он обновляет существующий
операционный deployment record и при наличии доступа вызывает
`$maintain-project-memory` в режиме **Checkpoint** для соответствующих
проектов. `$project-documentation` в режиме **update** требуется только
когда реально изменились поддерживаемые документы приложения. Успешный
релиз не требует дополнительного HANDOFF. Если Docker обновлён, а запись
в память не удалась, статус должен быть `DEPLOYED_RECORD_SYNC_PENDING`.

`project_managed` — стратегия управления версиями, а не новый класс
безопасности. Сервис `MANUAL` требует отдельного целевого поручения,
а обычная команда `deploy-project` **не отменяет `NO_TOUCH`**.

Описание процесса: [project-deployment.md](skills/maintain-server-containers/references/project-deployment.md).
[Синтетический пример политики](examples/project-managed.yaml).
Встроенный Python CLI проверяет опциональную политику
`release_management`, но **не выполняет развёртывание**.

## Политика проекта

Каждый проект хранит свои параметры в `maintenance/services.yaml` или другом явно определённом policy-файле. В публичном репозитории есть только вымышленный пример [examples/services.yaml](examples/services.yaml).

Схема v1 задаёт имена Compose-сервисов, владельца, текущий и целевой image, пользовательское состояние, необходимость backup, правила отката, health и smoke-тесты.

Подробности в [описании схемы](skills/maintain-server-containers/references/policy-schema.md). Если проект уже использует свой вариант `services.yaml`, его совместимость необходимо отдельно проверить, а не предполагать по имени файла. Для дополнительных правил безопасности предусмотрен [контракт доверенного адаптера](skills/maintain-server-containers/references/safety-adapter.md). Без зарегистрированного адаптера CLI отклоняет неизвестные правила; YAML не может сам загружать Python-код.


### Названия компонентов в группах зависимостей

В составном стеке логическое имя компонента может отличаться от имени службы
Docker Compose. Для такого случая в **политике самого проекта** предусмотрено
явное поле `component_aliases`. Агент не должен угадывать соответствие по
дефисам, подчёркиваниям и названиям контейнеров. Пример приведён в
[описании схемы](skills/maintain-server-containers/references/policy-schema.md)
и [синтетической конфигурации](examples/native-policy.yaml).
Если обязательный участник группы не определён, валидация не проходит и
автоматическое обновление блокируется.

## Категории обслуживания

| Категория | Поведение |
| --- | --- |
| `AUTO_SAFE` | Допускается ограниченное обновление при доказанной сохранности state и безопасном rollback |
| `AUTO_GATED` | Допускается после обязательных проверок backup, восстановления, миграций и совместимости |
| `MANUAL` | Только аудит и планирование в общей волне |
| `PIN_ONLY` | Закрепление того же содержимого image за точной версией/digest |
| `NO_TOUCH` | Исключение из штатных операций |

Сервисы с внешним администратором или неизвестным владельцем не обновляются автоматически. Группа сервисов с опасной зависимостью наследует более строгое правило.

## Сохранность данных

**Контейнер можно пересоздать. Пользовательское состояние нельзя терять или заменять.**

Перед обновлением нужно определить реальные Docker volumes, bind mounts, базы данных, пользователей, загруженные файлы, ключи и настройки. Новому контейнеру должны подключаться те же persistent sources. Возврат старого image не считается достаточным откатом, если новая версия уже изменила схему БД.

Существование архива не равно проверенной возможности восстановления. Подробнее см. [регламент обслуживания](skills/maintain-server-containers/references/maintenance-protocol.md).

## Разрешения без лишних вопросов

Одно явное поручение на ограниченную волну покрывает штатные pull/build, recreate, health, smoke и безопасный rollback. Повторное согласование не требуется, пока агент не выходит за указанные границы.

Отдельное разрешение необходимо для разрушительных операций, расширения scope, изменения внешнего доступа и сервисов, находящихся вне автоматической политики. Системные запросы разрешений самой среды агент не отключает.

## Ограничения v0.2.0

Сейчас реально выполняются в коде проверка политики и read-only анализ. Проверка свежести релизов, миграций, backup/restore и smoke-тесты остаются workflow агента и адаптеров проекта. Полностью автоматический, детерминированный исполнитель обновлений ещё **не реализован**. Это намеренное разграничение, чтобы не выдавать незавершённый механизм за безопасный production updater.

Следующая версия может добавить исполнитель, когда его безопасность будет проверена на временных Docker-стеках, включая искусственные ошибки, rollback и восстановление state.

## План развития жизненного цикла и резервного копирования

В [плане развития](docs/ROADMAP.md), [проекте контрактов жизненного цикла и восстановления](docs/LIFECYCLE-RECOVERY-DESIGN.md) и [спецификации одноразового тестового стенда](docs/DISPOSABLE-TEST-HARNESS.md) описаны будущие задачи: типизированная модель данных, контрольные точки резервного копирования, изолированное восстановление, ограниченный исполнитель и безопасный вывод приложений из эксплуатации. **Это предложения, а не реализованные возможности v0.2.0.** Текущая CLI остаётся read-only, правила безопасности не меняются.
